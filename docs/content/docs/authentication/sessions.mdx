The `SessionManagementPlugin` provides endpoints for querying, listing, and revoking sessions. Sessions are created automatically during sign-up, sign-in, passkey authentication, and successful 2FA completion.

## Setup

These examples assume you've already defined `AppAuthSchema`. If you want a complete setup from entity definitions through Axum mounting, start with the [Axum integration guide](/docs/integrations/axum).

```rust
use better_auth::plugins::SessionManagementPlugin;

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(SessionManagementPlugin::new())
    .build()
    .await?;
```

### Plugin Options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `enable_session_listing` | `bool` | `true` | Allow `GET /list-sessions` |
| `enable_session_revocation` | `bool` | `true` | Allow revocation endpoints |
| `require_authentication` | `bool` | `true` | Require a valid session for plugin endpoints |

## Opaque Session Tokens

Better Auth generates 32-character opaque session tokens. The browser sends a
signed `better-auth.session_token` cookie; the signature is verified before the
stored token can authenticate a request. Session endpoints do not accept a bare
`Authorization: Bearer` header. The bearer plugin is a separate capability.

The optional JWT surface provides signed tokens separately from these session
tokens. Trusted Rust code can read persistent state through `SessionManager` and
the configured store.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/get-session` | Return the current session and user |
| `POST` | `/get-session` | Refresh the session and remove expired rows when deferred refresh is enabled; otherwise 405 |
| `POST` | `/sign-out` | Revoke the current session and clear cookies |
| `GET` | `/list-sessions` | List all active sessions for the current user |
| `POST` | `/revoke-session` | Revoke one specific session by token |
| `POST` | `/revoke-sessions` | Revoke all sessions for the current user |
| `POST` | `/revoke-other-sessions` | Revoke every session except the current one |

## Session Lifecycle

1. A session is created after successful authentication.
2. The opaque token and session metadata are stored in the database.
3. The token is returned to the client and usually set as a cookie.
4. Authenticated requests resolve the token back to the stored session.
5. Expired or revoked sessions stop authenticating requests.

## Refresh Behavior

Session refresh is controlled by `SessionConfig`:

```rust
use better_auth::AuthConfig;
use better_auth::config::SameSite;
use chrono::Duration;

let mut config = AuthConfig::new("secret...")
    .base_url("https://auth.example.com");
config.session.expires_in = Duration::days(7);
config.session.update_age = Some(Duration::days(1));
config.session.disable_session_refresh = false;
config.session.defer_session_refresh = false;
config.session.fresh_age = Some(Duration::minutes(10));
config.session.cookie_name = "better-auth.session_token".to_string();
config.session.cookie_secure = true;
config.session.cookie_http_only = true;
config.session.cookie_same_site = SameSite::Lax;
```

- `update_age = Some(duration)`: refresh when the persisted expiry minus `expires_in` plus `duration` is due. Updating another session field does not reset this threshold.
- `update_age = None`: refresh on every access.
- `disable_session_refresh = true`: never refresh automatically.
- `defer_session_refresh = true`: `GET /get-session` leaves the row unchanged and reports `needsRefresh`. `POST /get-session` refreshes a due session or deletes an expired row. Both methods clear expired browser cookies.
- `fresh_age`: defaults to one day and checks session creation time for session listing. `None` or zero disables the freshness restriction.

Credential sign-in with `rememberMe: false` issues a one-day stored session,
a browser-session cookie and a signed `dont_remember` preference. A nonempty
verified preference suppresses refresh. For duplicate cookies, the first value
is authoritative. The `disableRefresh` query uses the pinned runtime's Boolean
coercion: even `disableRefresh=false` is a nonempty string and suppresses refresh.
An empty query value permits refresh.

Nested session middleware forwards renewal and cleanup cookies. Sensitive
revocation endpoints read the persisted signed-cookie session even when a
plugin has established a virtual session. Revoking another user's token returns
`status: true` and leaves that user's session unchanged. A session deleted during
a refresh returns `401 FAILED_TO_GET_SESSION`, rather than authenticating the old
snapshot; store failures return `500 FAILED_TO_GET_SESSION` from `/get-session`.

## Using Sessions in Axum Handlers

With the `axum` feature, use the `CurrentSession` extractor to access the authenticated user directly in your handler:

```rust
use axum::Json;
use better_auth::integrations::axum::CurrentSession;
use better_auth::prelude::{AuthSession, AuthUser};

async fn profile(session: CurrentSession<AppAuthSchema>) -> Json<serde_json::Value> {
    Json(serde_json::json!({
        "user_id": session.user.id(),
        "session_token": session.session.token(),
    }))
}
```

Use `OptionalSession<AppAuthSchema>` for routes that should work for both authenticated and anonymous users.

## Two-Factor Interaction

When 2FA is enabled, sign-in verifies the primary credential first and then pauses on a pending verification flow. A full session is only created after `verify-totp`, `verify-otp`, or `verify-backup-code` succeeds.

## Security Notes

- Session tokens are generated with `OsRng`.
- Cookie transport should normally keep `Secure`, `HttpOnly`, and `SameSite` enabled.
- Session records can retain audit metadata such as IP address and user-agent.
- Users can hold multiple sessions across devices and revoke them selectively.

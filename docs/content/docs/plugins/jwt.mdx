---
title: JWT and JWKS
description: Issue asymmetric session JWTs and publish their verification keys.
---

`JwtPlugin` signs session JWTs with a persistent keyring and publishes public
verification keys. The default algorithm is EdDSA with Ed25519. ES256, ES512,
RS256, and PS256 are also supported.

## Setup

The store must implement `JwkStore`. The bundled SeaORM migrator creates the
`jwks` table; application-owned stores must persist each key's identifier,
public and private JSON material, creation and expiry dates, algorithm, and
curve. Private keys are encrypted with the authentication secret by default.

```rust
use better_auth::plugins::jwt::{JwtAlgorithm, JwtKeyPairConfig, JwtPlugin, JwtPluginConfig};

let plugin = JwtPlugin::with_config(JwtPluginConfig {
    key_pair: JwtKeyPairConfig {
        algorithm: JwtAlgorithm::Es256,
        ..Default::default()
    },
    ..Default::default()
});

let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(plugin.clone())
    .build()
    .await?;
```

## Client behavior

Paths are relative to the configured authentication base path.

| Endpoint | Authentication | Response |
|----------|----------------|----------|
| `GET /jwks` | Public | `{ "keys": [...] }`, containing public JWKs |
| `GET /token` | Session required | `{ "token": "..." }` |

An authenticated `GET /get-session` also returns a JWT in `set-auth-jwt` and
exposes that header through `access-control-expose-headers`. Set
`disable_setting_jwt_header` to disable that hook.

Session JWTs contain the returned user fields, `sub` with the user identifier,
`iat` with the issue time, and `exp` fifteen minutes later. Issuer and audience
default to the configured base URL. `DefineJwtPayload` and `DefineJwtSubject`
allow applications to replace the session payload and subject.

## Configuration

| Field | Default | Behavior |
|-------|---------|----------|
| `jwks_path` | `/jwks` | Public key endpoint path |
| `key_pair` | EdDSA / Ed25519 | Primary signing algorithm; RSA defaults to 2048 bits |
| `additional_key_pairs` | Empty | Algorithms provisioned on first explicitly pinned use |
| `rotation_interval` | None | Expiry assigned to newly created signing keys |
| `grace_period` | 30 days | Public retention after a signing key expires |
| `disable_private_key_encryption` | `false` | Store private JWK JSON directly |
| `claims` | Base URL issuer/audience, 15 minutes | Default JWT claims |
| `keyring` | Store-backed | Application-owned `JwtKeyring` callbacks |
| `remote_signer` / `remote_url` | None | Delegate signing and serve public keys externally |

When an unpinned key expires, signing provisions a replacement. Explicit key
pinning fails for unknown, mismatched, or expired keys. Public JWKS retains old
keys through the grace period; the trusted verifier reads persisted keys,
including keys beyond public retention. Remove an old row when verification
with it must stop.

## Trusted server operations

Keep a clone of the plugin for application-owned signing and verification:

```rust
use better_auth::plugins::jwt::JwtSignOptions;
use serde_json::json;

let payload = json!({ "sub": "service-account", "permission": "read" })
    .as_object()
    .cloned()
    .unwrap_or_default();
let token = plugin
    .sign_jwt(payload, &JwtSignOptions::default(), None, auth.context())
    .await?;
let verified = plugin
    .verify_jwt(&token, None, None, auth.context())
    .await?;
```

`sign_jwt`, `verify_jwt`, `create_jwk`, and `resolve_signing_key` are Rust
interfaces. They do not add public signing or verification HTTP endpoints.
Signing preserves explicit claims and fills missing issuer, audience, and
expiry; it adds no `iat` unless supplied. Invalid signatures, keys, critical
headers, or verified claims produce `None` from `verify_jwt`.

JWT-backed core session cookie caching remains a separate integration boundary.
This managed-keyring slice does not expose an automatic cache configuration option.

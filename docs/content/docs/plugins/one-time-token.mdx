---
title: One-Time Token
description: Transfer an existing authenticated session through a single-use credential.
---

`OneTimeTokenPlugin` issues a short-lived credential that resolves to an existing
session. Consuming it preserves the original session identifier, token, user,
and expiry.

## Setup

```rust
use better_auth::plugins::one_time_token::{
    OneTimeTokenConfig, OneTimeTokenPlugin, OneTimeTokenStorage,
};

let plugin = OneTimeTokenPlugin::with_config(OneTimeTokenConfig {
    storage: OneTimeTokenStorage::Hashed,
    ..Default::default()
});
let auth = BetterAuth::<AppAuthSchema>::new(config)
    .store(store)
    .plugin(plugin.clone())
    .build()
    .await?;
```

## Client behavior

Paths are relative to the configured authentication base path.

| Endpoint | Authentication | Response |
|----------|----------------|----------|
| `GET /one-time-token/generate` | Session required | `{ "token": "..." }` |
| `POST /one-time-token/verify` | Token in JSON body | `{ "session": {...}, "user": {...} }` |

The default credential contains 32 random characters and expires after three
minutes. It is stored as a verification record whose value is the existing
session token. In hashed mode, the identifier contains the SHA-256 base64url
digest of the credential.

Successful verification consumes the record and sets the existing session
cookie. Replay and expired credentials fail. A revoked or expired underlying
session also fails after the credential is consumed. When several records
share an identifier, consumption selects the newest record and deletes its
older siblings.

The receiving browser's nonpersistent session preference is preserved. The
pinned runtime sets its session cookie before rejecting an expired underlying
session; this implementation preserves that ordering.

## Configuration

| Field | Default | Behavior |
|-------|---------|----------|
| `expires_in` | 3 minutes | Credential lifetime |
| `storage` | `Plain` | Plain, SHA-256, or application-owned `HashOneTimeToken` |
| `generator` | Random 32 characters | Async `GenerateOneTimeToken` callback |
| `disable_client_request` | `false` | Reject client generation while retaining trusted server generation |
| `disable_set_session_cookie` | `false` | Return the resolved session without authenticating the receiving browser |
| `set_ott_header_on_new_session` | `false` | Add `set-ott` to responses that create a session |

The generator receives the authenticated session and optional request. A
custom storage hasher runs consistently during issuance and consumption.
Stores must implement atomic `consume_verification_by_identifier` behavior so
concurrent requests cannot consume one credential twice.

## Trusted server operations

`generate_for_session` accepts an application-authenticated
`OneTimeTokenSession`; `verify_token` consumes a credential and returns that
same underlying session. These are Rust interfaces, with no additional public
authentication endpoints. Trusted generation remains available when
`disable_client_request` is enabled.

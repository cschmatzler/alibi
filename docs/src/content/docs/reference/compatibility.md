## The contract

HTTP behavior targets **better-auth@1.7.27**: the same endpoints, request and response shapes, status codes, error codes, redirects and cookie attributes. The official TypeScript client therefore works against an Alibi server without changes, and so do existing database rows and password hashes (scrypt in the TypeScript format).

Newer upstream documentation may describe behavior added after 1.7.27; it is outside the target until the pin moves.

Rust releases use independent Semantic Versioning and record the exact upstream target separately, so fixes can ship independently while retaining the upstream contract. See the [release policy](/guides/releases/) for versioning and compatibility rules.

## How parity is verified

Parity is established by **one mechanism**: a differential suite that runs the *official client* against **both** the pinned TypeScript runtime and this implementation, then compares everything they return and store.

- Scenarios run sequentially against fresh state on each server. Values, response shapes, status codes, redirects and cookies are compared; cookie security attributes are compared without exceptions.
- Generated identifiers and opaque tokens are compared through a bijection (repeated references and token rotation must agree). Dates must be valid and lifetimes agree within a small execution tolerance.
- Password scenarios import real hashes produced by each runtime into both stores and exercise sign-in, Unicode normalization and credential replacement.
- A software authenticator produces genuine WebAuthn signatures for the passkey scenarios; encrypted account and session cookies are authenticated with the published decoders; Chromium checks real browser cookie behavior.
- Negative controls prove the comparator catches drift.
- The route inventory test fails when the router's routes differ from `capabilities.json`, which lists every upstream route together with the scenarios proving it. All 151 inventoried routes are implemented.

Unit and integration tests check the Rust implementation on its own terms and do not claim parity. The full contract and how to run it are in the [compatibility guide](https://github.com/cschmatzler/better-auth-rs/blob/main/tests/compat/README.md).

## Native Rust APIs

Everything that is not an HTTP contract is native and may differ from TypeScript:

| Area | Native design |
| --- | --- |
| Schema | Application-owned models and `AuthSchema`, generated by the [CLI](/reference/cli/), instead of adapter-managed tables |
| Configuration | Typed `AuthConfig` and per-plugin config structs; numbers that mirror JavaScript numbers are `f64` |
| Plugins | The `AuthPlugin` trait ([Writing a plugin](/guides/writing-a-plugin/)) |
| Callbacks | Async trait objects with a `CallbackContext` (delivery, hooks, resolvers) |
| Server API | Typed `dispatch_endpoint` operations instead of `auth.api.*` ([Server-side calls](/guides/server-side-calls/)) |
| Integrations | [Axum](/integrations/axum/) and [Poem](/integrations/poem/) adapters and extractors |
| Storage | [SQLx](/databases/sqlx/) and [SeaORM](/databases/seaorm/) stores, [no-database mode](/databases/no-database/), [secondary storage](/concepts/secondary-storage/) |
| Extra operations | `openapi_spec_with_native_extensions()` lists Rust-only operations |

Where Rust needs a different shape, behavior stays observably the same on the wire: for example `AuthError::Api` produces the same `{code, message}` envelope as an `APIError`.

## Implemented

- All core routes: sign-up/sign-in, sessions, user and account management, password reset, email verification, OAuth and token endpoints.
- All bundled plugins: admin, anonymous, bearer, CAPTCHA, custom session, device authorization, email OTP, Have I Been Pwned, JWT, last login method, magic link, multi-session, OAuth popup, OAuth proxy, One Tap, one-time token, OpenAPI, organization (teams, dynamic roles), passkey, phone number, SIWE, two-factor, username — plus the API-key and passkey packages.
- All 36 built-in social providers and generic OAuth/OIDC with discovery.
- Cross-cutting behavior: managed secrets, dynamic base URL and trusted origins, cookie caches (compact, JWT, JWE), stateless sessions, secondary storage, rate limiting with shared backends, background tasks, database and endpoint hooks, additional fields.
- Separately published packages: `@better-auth/oauth-provider` (acting as an OAuth 2.1/OIDC authorization server, including client ID metadata documents from `@better-auth/cimd`), `@better-auth/sso` (OIDC and SAML provider management) and `@better-auth/scim` (SCIM 2.0 provisioning). Their differential scenarios live under `tests/compat/client-tests/tests/plugins/`; their routes are outside the core route inventory above.

## Out of scope

These upstream packages are explicitly **not** implemented and have no planned work:

| Package | What it is |
| --- | --- |
| `@better-auth/mcp` | MCP resource-server helpers on top of the OAuth provider |
| `@better-auth/stripe` | Stripe subscriptions |
| `@better-auth/i18n` | Translated error messages |
| `@better-auth/expo`, `@better-auth/electron` | Mobile and desktop client integrations |

Alibi both consumes OAuth/OIDC providers (including enterprise IdPs through [Generic OAuth](/authentication/generic-oauth/) and SSO) and, with the OAuth provider plugin, acts as one. Redis storage and native framework integrations are covered separately from the upstream profiles.

## Known boundaries

- **Token encoding.** Only current-format ciphertext is supported. Earlier Rust encodings and plaintext imports are rejected; no conversion API is provided.
- **Concurrent device decisions** and a few other races retain the behavior measured on 1.7.6, unchanged through 1.7.12, including its edge cases.
- The TypeScript generic-OAuth client helper `signIn.oauth2` is not served; use `signIn.social` ([Generic OAuth](/authentication/generic-oauth/#frontend)).
- **Change-password session replacement.** With `revokeOtherSessions`, revocation and the password write commit in one transaction as upstream's do, but the replacement session is created after that commit rather than inside it.

## Upgrading from 1.7.18

1.7.27 accepts bodyless `POST` requests that arrive as an empty stream without `Content-Type`, and `/get-session` ignores its body. Anonymous sign-in now enforces `trustedOrigins` like the other sign-in routes. Email sign-up sends its verification message after the user is committed: a delivery failure is logged and the sign-up still succeeds, so reject sign-ups with a `user.create.before` hook instead. Revoking your current session, revoking all sessions, and deleting a user by token now expire the session cookies. Expired verification rows are swept at most once a minute, and a lookup that finds its own expired value deletes it. On PostgreSQL `text` columns, new user JSON arrays are stored as standard JSON rather than array literals.

Several error codes changed: `/device/token` answers a rejected client with `invalid_client`, `getInvitation` answers missing, expired or non-pending invitations with `INVITATION_NOT_FOUND`, and SIWE returns a generic 401 without internal error details. The first unpinned JWT signature after upgrading can create a key for `jwks.keyPairConfig.alg`, which changes `alg` and `kid` for later ID tokens and session JWTs; earlier tokens still verify by `kid`. When a wildcard `allowedHosts` entry covers the passkey `rpID`, passkeys are accepted only from exact `allowedHosts` entries, the fallback origin, or exact `trustedOrigins` entries. Custom SIWE stores must insert the wallet inside the sign-up transaction, and custom SCIM stores need native transactions; without them SCIM routes answer 501. Deleting an organization now happens before the active selection is cleared, which matters if a restrictive foreign key points at the active organization.

Social providers accept account fields that are stored on create, link and sign-in. Kakao uses PKCE and accepts native-app ID tokens. Authorization URLs keep the provider's published query text. Generic OAuth sends `discoveryHeaders` only to the discovery origin and sends `authorizationHeaders` on refresh. A refresh refused with HTTP 200 now fails instead of returning the expired token. SAML Single Logout works for sessions past their first expiry; sessions whose logout record is gone fall back to the NameID on the SAML account without a SessionIndex. The SCIM managed-connection events list accepts `limit`, `offset` and `sortDirection` and returns `total`.

Alibi now always rejects SAML assertions encrypted with 3DES, regardless of `onDeprecated`.

For the OAuth provider, refresh tokens without `offline_access` stop working when their session ends, and a token request that fails validation no longer spends its authorization or device code. Client secrets must carry the configured prefix. Client metadata is written as a JSON object; rows stored as strings are still read. Client ID Metadata Document refreshes clear keys and post-logout redirect URIs the document no longer lists. Discovery reports an `http` issuer as configured; `http` redirect URIs outside the defaults need `allowInsecureRedirectUri`. No database migration is needed; the schema is unchanged.

## Upgrading from 1.7.12

1.7.18 binds email-change proofs to the user who requested them, separates phone OTPs from other verification records, and checks stored session authority before changing sign-in methods. Email signup can no longer set a phone number; use phone OTP verification instead. Request new phone OTPs and email-change links after upgrading, and restart pending OAuth account-linking flows. Bulk session revocation also rejects cached sessions missing from the session index. Passkeys use server-configured origins rather than the request's Origin header, and organization invitation lists require invitation-creation permission. No database migration is needed; the schema is unchanged.

## Upgrading from 1.7.7

1.7.12 tightens ID-token verification for social, One Tap, OAuth proxy and OIDC SSO sign-in: tokens must carry `iss`, `sub`, `aud`, `exp` and `iat`, 30 seconds of clock skew is accepted, and a provider without a client ID rejects every ID token. Set `client_id` on every provider used for ID-token sign-in. `SameSite=None` and `Partitioned` cookies are now always `Secure`. A failed password reset no longer spends its link or OTP: the proof, session revocation and password write share one database transaction (verification values kept only in secondary storage are still spent up front). No database migration is needed; the schema is unchanged.

## Upgrading from 1.7.6

1.7.7 separates OAuth state, proxy state, proxy packages, and proxy profiles by encryption purpose. Upgrade servers sharing the verification store and OAuth proxy participants together. Request new Magic Links and restart pending OAuth flows: old verification identifiers and ciphertexts are deliberately rejected. Existing account credentials, password hashes and session records need no migration for this release change.

## Checking a deployment

`GET /api/auth/open-api/generate-schema` (with the [OpenAPI plugin](/plugins/open-api/)) or the [HTTP API reference](/reference/http-api/) lists exactly the routes your instance serves. Run the differential suite locally with `./scripts/compat.sh` ([Contributing](/guides/development/)).

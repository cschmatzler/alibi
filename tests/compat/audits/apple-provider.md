# Apple provider authority (issue #139)

## Published contract and evidence owner

Pinned Better Auth 1.7.6 actually published `@better-auth/core/dist/social-providers/apple.mjs`, `oauth2/validate-authorization-code.mjs`, `oauth2/utils.mjs`, `oauth2/verify-id-token.mjs`, and Better Auth `context/create-context.mjs` / `api/routes/sign-in.mjs` are the independent authority. The new `oauth/apple.test.ts` official-client owner invokes that unchanged actual factory through Source fixture profiles. Only fixed trusted Apple token/JWKS destinations redirect to local HTTP. Controls supply synthetic signed credentials and real endpoint responses, never acceptance results, receipts or stored rows. Native profiles configure the public `AppleOptions` / `OAuthProvider::apple_with_options` and real SeaORM SQL. The existing social-provider state observer retains all account, user and session columns including foreign owners.

Authoring gate: the owners protect default/configured authorization, actual signed JWT admission and profile persistence, callback replay, refresh ownership, and genuine key retirement. Credible failures are missing factory defaults/JWKS, trusted subject replacement, accepting another audience or bad signature, and writing another owner's tokens. Existing generic or configured-verifier tests do not execute Apple's factory or Apple key/nonce/subject policy. These are table owners at the SDK/HTTP/SQL boundary; no test-only production exports or bypasses were added. Trusted JWKS transport configuration is a production application interface for HTTP/cache policy.

## Interface and policy

`OAuthProvider::apple(client_id, secret)` uses Apple authorization/token endpoints, default ordered `email name` scopes, PKCE S256, hybrid `code id_token` and `form_post`. `AppleOptions` supports client ID arrays, configured scopes and default-scope suppression, explicit audience, bundle audience fallback, ID-token disabling, trusted JWKS transport, and profile mapping. Primary ID alone authenticates code/refresh POST; all configured IDs are accepted by direct ID-token verification when no stronger audience option exists. Generic returned-provider fields support application user-info, verifier and refresh callbacks; disabling ID tokens dominates verifier override.

The published Apple factory ignores loginHint, prompt and nonce in authorization inputs. It has no configured issuer override or provider logout, no userinfo HTTP endpoint, and no factory fallback expiry. Local session sign-out uses the common runtime. `disableSignUp` is not propagated by this pinned factory/context: only `disableImplicitSignUp` is copied into the configured provider, and explicit `requestSignUp` overrides that implicit restriction. The native returned provider additionally exposes its common explicit signup policy; that is not claimed as an Apple option parity case.

Apple direct tokens require the actual declared JWK/header algorithm, literal matching kid, issuer `https://appleid.apple.com`, configured audience and iat age <= one hour, optional exp/nbf, and exact or SHA-256 hexadecimal nonce when requested. The issued JWT's original bytes are verified; untrusted kid/issuer never select an HTTP URL. This extraction also retains OneTap's distinct all-matching-key policy. Google shared policy follow-ups are coordinated with issue #228, rather than fabricating Apple-specific verifiers.

Code exchange decodes the returned ID token for profile data as the published Apple factory does; it does not add a verification step absent in Source. Apple callback `iss` does not become a provider issuer policy. Refresh uses actual grant_type/client_secret_post and preserves owned account identity, scope and sessions while rotating stored access/refresh/ID tokens.

Subject is original `sub`, independently of user mapping. Supported string and finite numeric subjects remain stable. Name defaults to JWT name or empty when absent/null/empty/falsy numeric zero; truthy numeric name is stringified by user persistence while the enriched original profile retains its numeric value. Supplied first/last name overrides JWT name and trims; enriched profile goes to application mapping. Application mapper cannot substitute raw account identity. Email absence/null/empty yields the same coded denial; verification accepts booleans or the exact string `true`; JWT picture is ignored by Apple default mapping. Arbitrary non-string email and object/array names are outside the declared profile shape and are not widened into admission contracts.

Shared transport parsing follows the published helper: absent/numeric-zero expiry has no fallback, fractional expiry keeps milliseconds; scopes accept whitespace-separated strings or arrays of trimmed strings, with commas retained inside a scope. Absent code-exchange scopes persist the empty join string; direct ID-token absent scopes retain their separate semantics.

## Reviewable observations and before evidence

Receipts retain actual request method, path, authorization/content-type and full form. The generated PKCE verifier is checked against the actual authorization challenge, retained reversibly as `{token,length}` under its original body key for existing opaque-token comparison. No comparator or allowlist changes were made. Full SQL rows and SDK/HTTP traces remain in every relevant scenario. Foreign owner rows are asserted identical, and denials do not write identities or credentials. Key rotation removes the actual matching key, proves rejection with rows intact, then restores the actual key and proves another legitimate session.

The feature did not have a compiling pre-fix dedicated Apple constructor. Prior-public-API evidence is therefore explicitly separate: `/tmp/better-auth-issue139-before` freezes production at main `effc327a` with the same local control/receipt scaffold and a prior public generic provider configured trusted Apple URLs, client/secret and email/name scopes. No verifier, profile-admission replacement or fake results are added. The primary real-source owners fail on that API for intended reasons: authorization uses `code` instead of Apple's hybrid response; genuine signed ID-token sign-in is `404 ID_TOKEN_NOT_SUPPORTED`. This is evidence for the missing dedicated capability, not a claim that the generic API has a dedicated factory.

Independent review caught truthy numeric JWT name being incorrectly discarded. The new numeric-name table owner passed Source and failed native at persisted `""` versus `"7"` before repair. The final implementation preserves the enriched original claim and typed persistence string. Logs: `/tmp/issue139-before-admission.log`, `/tmp/issue139-numeric-name-before.log`.

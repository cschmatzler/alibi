# Signup and password policy configuration (issue #182)

The contract is the published Better Auth 1.7.6 implementation in `api/routes/{sign-up,sign-in,password}.mjs` and `context/create-context.mjs`. This lane owns signup enablement, automatic sign-in, synthetic duplicate responses, configured hash/verifier and existing-user/customization callbacks, initialized UTF-16 password bounds, and the password reset delivery/proof lifecycle. Additional user-field policy (#184), validateUserInfo (#183), and email-change/deletion policy (#186) remain separate owners.

## Production behavior

Disabled email/password signup keeps its public route and rejects with the Source coded 400 before crypto or persistence. Disabling email/password sign-in rejects before handler email validation. Signup hashes with the real configured hasher before duplicate decisions and before the application create hook. Sign-in checks only the upper password bound before lookup, uses the selected canonical credential, and performs the real configured hash for unknown, absent, null, or empty credentials before returning the generic invalid-password rejection.

When automatic sign-in is disabled or email verification is required, an existing email produces a fresh synthetic user with no physical user, credential, session, or cookie issuance. The existing-user callback receives the actual physical user and request; its failures are masked by the normal notification contract. A typed create-user 403 uses this same synthetic fallback only under that enumeration-safe policy. A false create hook still rejects with FAILED_TO_CREATE_USER, and ordinary hook errors retain the Source rejection. Custom synthetic callbacks receive core fields and a generated ID; output is filtered through the registered public core/plugin schema and callback failures propagate. **`additional_fields` is empty here because these application profiles configure no additional user schema. This lane does not claim arbitrary additional-field support.**

Password bounds count UTF-16 code units. Configured zero minimum/maximum initialize to 8/128, matching Source's effective configuration, and the initialized extension is available to reset and the trusted server-only setPassword owner. Reset proof duration defaults to one hour; an explicit nonzero chrono duration supports sub-hour application configuration, and zero retains the effective default. The existing hours builder remains available.

Reset delivery URLs include the configured auth base path. Delivery receives the initialized, registered user schema and actual request context. Delivery errors are masked. Reset checks token presence before password bounds, accepts the Source empty-body-token/query-token fallback, then atomically consumes the physical proof. Expired or missing-user proofs are consumed before crypto or callbacks; missing users retain the coded USER_NOT_FOUND rejection. Hasher failure never restores the consumed proof. The real canonical credential write precedes the awaited onPasswordReset callback; callback errors propagate before optional session revocation. Successful resets retain or revoke physical sessions according to configuration, and replay cannot change credentials or invoke another callback.

The shared owned-notification helper extracts the existing API-key background work implementation without changing its task ownership. The default path awaits completion; a configured background observer receives already running work, and dropping that completion or throwing from the observer does not cancel the task. Existing API-key background owners are retained and were rerun in the full SDK suite.

## Owning proof and authoring gate

The application fixtures instantiate actual published `betterAuth` and native public plugins over real SQLite stores. Their controls configure genuine application callbacks, inspect full physical users/accounts/sessions/verifications, or deliberately retire actual credentials/proofs. Hash callbacks use the real Source/native scrypt algorithms; published Source `verifyPassword` independently verifies native stored digests. Complete SDK observations and raw HTTP traces remain under the unchanged comparator and allowlist. Hash bytes and token relationships stay in the existing identity domains with encoding/length evidence; null and empty credential values stay literal. No fake crypto, supplied authentication receipt, test-only production interface, or narrowed observation was added.

Configured owners exercise callback ordering, request context, typed/ordinary errors, custom output filtering, UTF-16 limits, effective defaults, proof duration, single-use races and replay, notification ownership, actual OTP signup override, registered username fields, and full foreign-principal isolation. Default signup/reset owners cannot observe these configured callback and physical-storage contracts. Each regression is at the real SDK/HTTP owning boundary; no duplicate private implementation tests were added.

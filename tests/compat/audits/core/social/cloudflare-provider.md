## Configuration and protocol

`OAuthProvider::cloudflare` / `cloudflare_with_options(CloudflareOptions)` uses `https://dash.cloudflare.com/oauth2/auth`, fixed `https://dash.cloudflare.com/oauth2/token`, and `https://api.cloudflare.com/client/v4/user`. Default scope is `user-details.read`; defaults, configured scopes and requested scopes retain first-occurrence order with exact duplicates removed. Disabled defaults with no other scopes omit `scope`. Authorization uses code/S256 PKCE and requires a client ID. An application authorization endpoint and callback URI override are supported. Request login hints, prompt, response mode, additional authorization parameters and ID-token nonce are not forwarded by this pinned factory. There is no configurable issuer/discovery endpoint.

Confidential clients default to `client_secret_basic`; both credentials are form-url-encoded before base64, including spaces, punctuation and colons. Explicit `client_secret_post` puts credentials in the form; public clients use `none`, client ID only, without a secret. The same method applies to code exchange and refresh. Invalid method/secret combinations fail before the token HTTP request. Token HTTP redirects are refused, as in the published token helpers. The primary owner includes an actual 307 with a provider receipt sink: the callback denies after one request, without reaching the sink or creating SQL rows. Missing/zero expiry persists null; finite fractional expiry retains millisecond precision. Refresh rotates the stored access/refresh credentials while retaining the original stored scope, matching the actual Source account route.

## Profile and unsupported capabilities

User information comes from the API success/result envelope, not the Cloudflare OIDC endpoint that only provides `sub`. A false success, absent/null result or HTTP error denies admission. Raw result `id` independently establishes the stable account subject. Missing/null/empty subjects deny without writes; finite numeric subjects use JavaScript number-string formatting. The mapper receives the original result and cannot replace its account ID.

Name is the truthy first/last names joined with one space, falling back to email when empty. Absent/null/empty names and numeric zero fall back to email; finite nonzero numeric names become strings. Default image is absent and default email verification is false. Absent/null/empty email denies before user creation. An application mapper can supply name/email/image/verified email. Arbitrary object/array profile fields and numeric email are outside the declared string profile shape; no parity claim is made for them. The generic returned provider's signup, verified-email and user-info overrides remain available.

The pinned provider has no ID-token/JWKS/audience/nonce verifier or provider logout. An untrusted ID token returns `ID_TOKEN_NOT_SUPPORTED` without HTTP or SQL effects. Invalid configured provider selection and unissued callback state likewise deny without provider requests or rows. The ordinary local logout owner revokes only its session without an outbound provider request. Cryptographic ID-token scenarios would exercise an unsupported feature; the actual PKCE verifier/challenge is independently checked instead.

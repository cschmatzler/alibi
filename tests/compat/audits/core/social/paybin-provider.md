# Paybin provider contract (issue #155)

Authority: published Better Auth **1.7.6** `@better-auth/core/dist/social-providers/paybin.mjs`, its declarations, account-subject resolver, authorization helper and code/refresh token helpers. The unchanged published Source factory runs on deterministic local HTTP: only its actual fixed issuer token destinations are redirected. Native uses `OAuthProvider::paybin` / `paybin_with_options(PaybinOptions)`. Controls supply grant responses, never callback admission or database rows. The official-client owner is `tests/core/social/paybin.test.ts`.

Authoring gate: this owner independently protects Paybin's issuer endpoint construction, PKCE grant, ordered scopes, decoded grant-profile fallback and original account subject. Credible regressions include normalizing issuer slashes, deduplicating scopes, dropping PKCE, using Basic credentials, fetching an invented userinfo URL, replacing raw subject with mapper ID, or inventing JWT verification. Other provider owners do not instantiate this factory. Mapping variants share one table; lifecycle cases retain actual transport and persisted owner/foreign rows. No production test-only seam is added. Optional `COMPAT_OBSERVATIONS_DIR` diagnostics retain both complete observations and raw traces before the unchanged comparator runs.

## Protocol

Issuer is `options.issuer || "https://idp.paybin.io"`. Authorization and token endpoints append `/oauth2/authorize` and `/oauth2/token` without trimming a trailing slash. Authorization endpoint and redirect URI overrides use nonempty configured values. Client ID and secret are required when authorization starts; PKCE is mandatory and the persisted verifier produces the observed S256 challenge. Default scopes are `openid email profile`, followed by configured then requested scopes, preserving duplicates and order. Disabled defaults remove only those defaults; no scopes omit `scope`.

Nonempty login hints and configured prompt are forwarded; allowed additional parameters can replace prompt. The official sign-in route rejects reserved state, client, redirect, scope, response-type, nonce and PKCE additions. `responseMode` is not forwarded by this factory. There is no discovery, userinfo endpoint, ID-token nonce generation, provider revocation or RP logout.

Code and refresh requests use client-secret-post; optional client key appears only in the code form. Code includes the state-owned PKCE verifier and configured/default callback URI. Refresh sends only refresh token and client credentials. Token redirects are refused. Absent and zero token expiry remain null; fractional seconds preserve milliseconds. Refresh rotates stored tokens while preserving existing scope, user rows, foreign accounts and sessions. Sign-out revokes only the local session and sends no provider request.

## Identity

Without a grant ID token, the factory returns no user information. Otherwise it **decodes** the JWT payload; it does not verify signature, issuer, audience, expiry or nonce. A real separately signed grant with foreign issuer/audience/nonce and expired claims is admitted, explicitly demonstrating the published limitation. Direct ID-token sign-in is unsupported and rejects before HTTP. There is no JWKS operation to exercise.

Account subject derives from the original `sub` independently of application mapping; missing/null/empty subjects deny and numeric subjects use JavaScript string formatting. The mapper receives the original payload before subject denial. Its mapped ID stays in public account-info output but cannot replace persisted account identity.

Name uses `name || preferred_username || ""`, retaining absent/null/empty/zero fallbacks and numeric values. Email is the original email; absent/null/empty denies admission. Image preserves absence, explicit null, empty and numeric values in account-info; typed persistence stores scalar strings. `emailVerified` preserves `email_verified || false` in raw output; native typed persistence matches Source's boolean conversion (numeric `42` persists false). Mapper fields override the public defaults. Unknown payload fields remain in account-info `data`.

## Measured failure contracts

The error owner is the same official-client table, extended to **87 scenarios / 3,632 assertions on each SQLx and SeaORM adapter**. The earlier two-case residual reproduction fails on both unchanged adapters; its complete observations remain archived. A broader pre-fix table also reproduces the failure-stage differences rather than inferring behavior from TypeScript declarations. The new retained contracts cover:

- Thirteen malformed grant inputs: two/four/five compact parts, empty payload, bad base64, invalid JSON, array/null claims, invalid UTF-8 and truthy number/boolean/array/object token values. The actual factory's `decodeJwt` exception escapes callback redirect handling: **empty HTTP 500, no Location and no clear-state cookie**. Database state has already been consumed; replay is refused without a second provider request. Direct ID-token sign-in remains independently unsupported and produces no provider HTTP.
- Missing, empty, zero, false and null grant tokens retain the absent-profile **302 `unable_to_get_user_info` with state-cookie cleanup**, using the configured callback error URL. These are not treated as malformed truthy JWTs.
- New-account truthy numeric/boolean/array/object email reaches the caught email lookup error: **302 `internal_server_error` on the default provider error URL**, ignoring the state-owned custom error URL, with cookie cleanup and no identity writes. Falsy zero/false email instead uses the custom callback URL and `email_not_found`. Raw subject failure precedes either email check. The real application mapper can replace numeric email with a string and admit the original raw subject; the original numeric claim remains in account-info `data`.
- An existing valid Paybin account with numeric email hits uncaught sign-in candidate validation before token/user mutation: **empty 500 with no cookie cleanup**. Explicit linking retains the trust guard first: unverified numeric email returns configured `unable_to_link_account`; verified number/zero/false email hits the non-null raw email type error and returns empty 500 before writes. The selected owner's existing session and all foreign credentials remain unchanged.

The callback opt-ins live in `OAuthAuthorizationPolicy`, default false, and are enabled by Paybin only. Effective mapped raw email is read from the existing public profile output; native `OAuthUserInfo.email` stays a string. No shared decoder, global schema, comparator relaxation, error string sentinel, or broad coercion was added. Default providers retain their existing callback behavior. Raw error bodies remain empty and contain no token, profile or exception details.

The retained owner checks complete users/accounts/sessions (including actual password bytes), grant receipts and PKCE, selected and foreign rows, actual verification absence after callback, replay refusal and exact error status/location/body/cookies. Twenty mutations of genuine captured observations (ten per adapter) are rejected by the unchanged comparison gate: wrong status/location/error code/clear cookie/private body, changed foreign ownership/password, removed foreign session, restored verification, and repeated token exchange. Genuine unmodified Source/native pairs compare cleanly before every mutation. These are evidence-integrity negative controls, not a claim of exhaustive instrumented Source branch coverage. Existing comparator/classification/trace/oracle harness controls also pass (45 tests / 419 assertions).

Self-review traces state-cookie authentication and verification deletion before grants; raw subject resolution before email handling; the explicit link trust/email order before account mutation; and the callback-only raw email checks. The new code reads existing account ownership only for anomalous effective email and returns before identity writes. The issuer endpoint and grant transport stay application-configured; direct proof remains unsupported. No authorization or data-exfiltration flaw was found in the bounded change.

Official [Paybin setup documentation](https://better-auth.com/docs/1.6/authentication/paybin) explains configuration and SDK usage, but the published **1.7.6** factory and route/helpers are the authority for these failure stages. All installed files from `better-auth`, `@better-auth/core`, and `jose` were compared with authentic registry tarballs before proof: 465, 350 and 80 files respectively, with zero differences. Dependencies were not mutated; no hardlinked Source inode was modified.

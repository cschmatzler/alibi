## Factory and native interface

`OAuthProvider::paypal` defaults to `PayPalEnvironment::Sandbox`; `paypal_with_options(PayPalOptions)` also supports `Live`. The actual default destinations are:

| Environment | Authorization | Token | Userinfo |
| --- | --- | --- | --- |
| Sandbox (default) | `https://www.sandbox.paypal.com/signin/authorize` | `https://api-m.sandbox.paypal.com/v1/oauth2/token` | `https://api-m.sandbox.paypal.com/v1/identity/oauth2/userinfo` |
| Live | `https://www.paypal.com/signin/authorize` | `https://api-m.paypal.com/v1/oauth2/token` | `https://api-m.paypal.com/v1/identity/oauth2/userinfo` |

No default, configured or requested scopes are emitted: the published factory passes literal `scopes: []` and never consumes the caller's scope argument. Order is therefore the empty sequence, even for duplicates and `disableDefaultScope`. Native's default-off `omit_scopes` authorization policy expresses this behavior without changing sibling defaults. `requestShippingAddress` is declared upstream but unused. Native does not invent an effective shipping-address or scope option.

Authorization requires nonempty client ID and secret; missing credentials deny before HTTP. It uses response type `code`, S256 PKCE, configured prompt truthiness, configured authorization endpoint and redirect URI. Additional parameters are forwarded after configured prompt, subject to the shared reserved-parameter guard. Factory login hint, response mode and nonce are absent even when supplied. There is no built-in issuer/discovery/JWKS/logout policy. A callback `iss` and ID-token issuer/audience/nonce/expiry do not acquire verification semantics from this factory.

Both authorization-code and refresh grants force encoded `client_secret_basic`. Credentials do not appear in their forms. Code exchange sends the actual 128-character verifier (its SHA-256 challenge is independently checked), code and effective redirect URI. The credential-only token options intentionally omit `clientKey`; configured redirect URI applies to code exchange, not refresh. Redirected token responses are refused before credentials can reach the redirect destination. Missing/zero expiry remains null; fractional expiry retains milliseconds. Native retains its ordinary public callback, signup and token policy interfaces.

## Profile, proof and persistence

GET userinfo appends `schema=paypalv1.1`, sends the real access-token bearer and `Accept: application/json`. HTTP failure/null profile/missing access token deny. Name, email, picture and `email_verified` are copied directly into raw account-info output, preserving absence, null, empty strings and measured numeric values. Typed persistence independently projects the native fields. Missing/null/empty/zero name becomes an empty stored name; nonzero numeric name/image becomes a string. Missing/null/empty email denies signup; image absence/null becomes SQL null while an empty image stays empty. Missing/null verified status becomes false; measured numeric zero/one stores false/true. The mapper receives the original complete profile, can override application fields and public ID, and runs before invalid account-subject denial.

Account identity comes from original `user_id`, independently of profile `sub` and mapper ID. Missing/null/empty/blank/`"null"` subjects deny. Numeric subjects, including zero, use JavaScript string formatting. The mapper's public ID cannot replace persisted account authority. Account-info reads return raw changed profile fields without admitting a replacement subject or rewriting stored rows.

If the trusted token exchange returns a nonempty ID token, the published factory **decodes** its payload and compares a truthy token `sub` strictly with `profile.sub ?? profile.user_id`. Null/missing profile `sub` falls back; empty `sub` blocks fallback. Malformed/non-object claims, missing/null/empty token subjects and type/value mismatches deny. Matching unsigned tokens, including wrong issuer/audience/nonce and expired claims, are accepted by this decode-only consistency contract. This is not signature, JWKS, nonce, audience or issuer verification. The factory has no direct ID-token verifier; untrusted direct sign-in returns `ID_TOKEN_NOT_SUPPORTED` before HTTP. Native preserves that distinction. Provider logout is unavailable; ordinary sign-out revokes only the local session and leaves accounts/tokens and foreign rows intact.

## Scope and explicit residuals

Issue #156 remains open. This PR proves the dedicated default/configured factory and measured typed profile domain, not arbitrary out-of-schema storage or every generic application override permutation. Dedicated asynchronous getUserInfo/refresh/verify callbacks, override-on-sign-in and encrypted-token permutations remain generic-owner coverage/residuals rather than PayPal-specific completeness claims. Coordinator-owned full-suite and instrumented Source coverage proof are not run by this worker.

A retained exploratory failure (`/tmp/paypal156-before.log`) shows Source's permissive SQLite path stores `email_verified: ""` as a string while native's Rust field is boolean. No blanket normalization, skip or comparator exception is added to hide this. The primary passing suite covers the declared boolean domain and numeric zero/one; empty-string verification and numeric email are independently proved at existing-account-info read boundaries, with full SQL state unchanged. New-admission numeric email and other arbitrary nonboolean verification values are outside this PR's parity claim. Closing these gaps requires an explicit policy for invalid upstream profile types while preserving native Rust interfaces.

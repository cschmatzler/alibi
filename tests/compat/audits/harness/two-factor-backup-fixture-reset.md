# Backup callback fixture reset

Independent review of frozen capability cae2fec found a fixture repeatability defect, not a production authentication defect. Its custom generator derives `same-N`/`other-N` from a real callback receipt map. That application map survived the existing database reset in both fixtures, so the unchanged official-client custom scenario failed against TypeScript itself on its second runtime invocation: expected `same-1` but received `same-4`. Source callbacks and published options were correct; database reset had left fixture-owned application state behind.

The source fixture remains callable and now exposes a reset method that clears only its backup receipt map. The native fixture shares its existing receipt handle with the main fixture reset closure; clearing that same map resets the actual custom generator count. Both methods are invoked at the existing `/__test/reset-state` boundary, alongside existing application controls. Configurations, callbacks, production modules, stores, response comparison and callback receipts within a scenario are unchanged. No callback input is synthesized, filtered or replaced.

The existing custom official-client owner now includes one bounded reset control after its original enrollment/consumption/regeneration lifecycle. It performs a second real signup and enrollment through the same application configuration, proves a new stored user ID, the actual custom codes and ciphertext, and exactly the new generator/encrypt/decrypt receipts. Other profiles retain their existing lifecycle. All original SDK results and actual transport entries remain; the newly read storage/view responses also remain in the complete raw transport observations. This is the primary owner of fixture reset acknowledgement and callback state isolation, with no duplicate primitive/reset-model tests.

The exact new control fails on fresh unchanged source and native servers: `/tmp/two-factor-backup-reset-ts-before.log` and `/tmp/two-factor-backup-reset-rust-before.log` both stop at the second enrollment, expected `same-1`/`other-1`, actual `same-4`/`other-4`. The original TS-to-TS counterexample is retained separately in `/tmp/two-factor-backup-review-self-control.log`.

After the repair, exact custom official-client source self-control passes 1 scenario/112 assertions in `/tmp/two-factor-backup-reset-ts-after.log`; native self-control passes 1/112 in `/tmp/two-factor-backup-reset-rust-after.log`. The focused source-versus-native backup family passes 7 scenarios/494 assertions in `/tmp/two-factor-backup-reset-sdk-final.log`. Actual fixture build and client TypeScript checks pass in `/tmp/two-factor-backup-reset-build.log` and `/tmp/two-factor-backup-reset-typecheck.log`; `git diff --check` passes. No inventory, lockfile, migration, schema, production or full-gate edits/checks belong to this repair.

The independent production review found no blocking issue in the bounded backup capability: factor lookup derives from the authenticated or signed challenge owner; replacement CAS filters exact factor ID and expected ciphertext; duplicate codes are all removed; regenerate updates only the selected row's backup field; callback decode errors restore attempt state whereas successful decode followed by encode failure burns it; pending disableSession omits its token, creates no session/trust record, and preserves the challenge while consuming codes and attempt state. Native failures compare actual user/factor/session/challenge rows and retries; official-client lifecycle controls protect persisted owner/token state and actual OTP completion. Extreme generator bounds and malformed/non-string installed JSON wire behavior remain explicitly unclosed in the parent audit.

# Set-active organization metadata: Better Auth 1.7.6

This follow-up repairs the confirmed set-active response projection. It does not claim complete set-active body/selector, cookie-cache, or denied-selection parity.

The pinned `better-auth/dist/plugins/organization/routes/crud-org.mjs::setActiveOrganization` checks membership, obtains `adapter.findOrganizationById`, updates the current session selection, sets its session cookie, and returns that organization row. `adapter.mjs::findOrganizationById` retains stored metadata text. Creation/update responses instead parse metadata; that difference is intentional upstream behavior. Rust previously used `OrganizationResponse::from_organization`, returning a parsed record on set-active. It now reuses the existing `from_stored_organization` projection used by owned get/full organization handlers. No storage, membership, cookie, selector, or session-update code changes.

Two official-client scenarios in `tests/organization-extensions/set-active-metadata.test.ts` own the observable result:

- An organization with nested record metadata, integer-like keys, large/tiny numbers, null/boolean array values, and an application key named `$serde_json::private::RawValue` returns the exact JavaScript stored JSON string. A second organization with an explicit empty record returns `"{}"`. Two real tokens belonging to the owner begin with different selections; selecting by ID and slug changes only the current token. Actual SQLite organization/member/metadata rows and both token scopes are observed throughout. Updating metadata and selecting again returns fresh stored text while preserving the logo, unrelated organization, memberships, and sessions.
- Absent metadata remains a present null field on the public set-active result, while creation still omits it. The actual owned membership and current session selection remain unchanged by reselecting. This control inspects its wire result and persisted membership/session state; the separate known SQL NULL versus literal JSON-null storage boundary is not normalized or claimed equivalent.

The record scenario fails against the frozen prior implementation (`c058da7`) at the first set-active result because metadata is an object instead of a string; the absent-metadata control remains green. After the shared projection repair, both pass (82 assertions).

# Compromised-password checking (issue #135)

Authority is the installed, unchanged Better Auth 1.7.6 `plugins/haveibeenpwned/index.mjs` and its published options, the installed betterFetch response parser, better-call's endpoint context, and the actual signup, reset, change-password and admin hash owners. `HaveIBeenPwnedPlugin`, its configuration and `PwnedPasswordClient` are public native APIs. A standalone `is_password_compromised` helper uses the published service. The plugin contributes no HTTP routes.

The Source plugin decorates the initialized original password hasher. Checks run at actual hash operations, before the original hasher, in reverse initialization order for nested decorations. Verification of an existing password does not run the checker. Defaults are the seven exact paths `/sign-up/email`, `/change-password`, `/reset-password`, `/email-otp/reset-password`, `/phone-number/reset-password`, `/admin/create-user` and `/admin/set-user-password`. Explicit empty paths check none; literal `*` has no wildcard meaning. Only enabled=false bypasses checking. An empty custom compromised message uses the published default. An explicitly included sign-in path checks the genuine missing-user timing hash, while returning credential verification remains unchanged.

Logical endpoint identity is distinct from an optional physical request. The measured actual Source server-only setPassword endpoint has no registered HTTP path; better-call normalizes its handler context to `virtual:`. Defaults and custom `/set-password` therefore bypass checking; explicitly configured `virtual:` checks it. `/tmp/issue-135-source-path.log` records the actual original hash callback's `/sign-up/email` and `virtual:` contexts. No set-password HTTP route is introduced. Disabled checks bypass absent context; enabled checks with a completely absent endpoint context fail, while a present empty path bypasses. The native public hash context supports genuine physical context and an explicit trusted server context; future logical server dispatch remains issue #205.

The helper computes uppercase SHA-1 from the original UTF-8 password and sends only its first five characters to a range service. Remaining 35 characters are compared locally. This runs before real scrypt NFKC normalization. Default destination is `https://api.pwnedpasswords.com/range/`; a replacement client/destination is trusted application configuration. Actual GET receipts prove Add-Padding=true, User-Agent=BetterAuth Password Checker, an empty body/query and no authorization/cookie/password/suffix. Production provider errors report status or the generic retry message, without echoing URL/password/suffix.

The first case-insensitive matching suffix line owns the result, including zero before a later positive duplicate. Matching counts must be canonical nonnegative JavaScript safe integer decimal strings. Leading zeros, signs, whitespace, fractions, exponents, nonfinite values and unsafe integers reject. Unrelated malformed lines do not. LF and CRLF are accepted; a lone final CR remains part of the count. Media parameters are stripped before classification, including an empty parameter tail. JSON and text media use the actual betterFetch JSON-or-raw-text behavior; parsed strings unwrap, other valid JSON and blob media reject. The helper owner measures normal JSON strings, non-string JSON, JSON with unpaired UTF-16 surrogates, parameterized JSON/XML, exact text case and provider status failures against actual HTTP responses. `/tmp/issue-135-range-probe.log` independently records Source/native malformed matching surrogate and positive-first-line/unrelated surrogate outcomes. The private UTF-16 response decoder preserves relevant ASCII range lines. Rust password strings are valid UTF-8; JavaScript password inputs containing lone UTF-16 surrogates are outside this input representation and are not claimed as universal parity.

Ordering is observable and retained. Signup hashes before identity validation and database creation, including enumeration-safe duplicate timing hashes. Change-password hashes the new password before current-password verification. Core reset consumes its real proof before hashing; email OTP and phone reset consume their real OTP before hashing. Checker or original-hasher rejection burns those proofs without password writes, successful-reset callbacks or revocation. A fresh clean proof reaches the original real hasher, persists that same hash, invokes the actual callback and revokes configured sessions. Admin creation creates its admitted user before hashing, so Source rejection may leave that real user without a credential. Admin set-password checks the target before hashing, returns the actual USER_NOT_FOUND 404 for a missing target, uses the initialized application hasher and creates a canonical credential when absent. Retained native tests previously asserting success for a missing target or no credential creation were corrected against the actual Source SDK/store owner, not removed. Reset notification callbacks receive the actual public user view. Merged identity validation and request authority ordering remain intact.

# Trusted setPassword operation (issue #185)

Pinned Better Auth 1.7.6 `api/routes/update-user.mjs` exports the server-only operation with `sensitiveSessionMiddleware`. The native public operation is `plugins::password_management::set_password(&AuthRequest, &str, &AuthContext) -> AuthResult<()>`; it has no target-user argument and registers no public auth route. It re-reads a signed-cookie physical session, bypassing cached and virtual authority, applies initialized UTF-16 password bounds, reads only the owner's canonical credential identity, hashes with the real initialized application hasher before existing-password denial, and creates or updates that row. Sessions remain active. Genuine storage and application hash errors propagate to the caller.

The official-client owner is `password-management/set-password.test.ts`. A private application bridge invokes the actual Source `auth.api.setPassword` or public native operation. Source/native profiles use the same minimal two-factor plugin schema and real configured scrypt callbacks. Private application failures preserve the actual application's 500 JSON representation; auth API coded errors retain their exact media type. This is controlled application integration, not a public authentication endpoint.

Twelve primary scenarios retain complete profile user/account/session rows, actual hash callback inputs/results, HTTP/SDK traces and foreign principals. They cover real credential creation and NFKC sign-in, null-password updates, initialized UTF-16 bounds, no-cookie denial, revoked/expired physical authority with still-positive cookie caches, actual foreign virtual session injection, replay, genuine callback/SQL trigger errors and recovery, and concurrent null-credential updates. Hash observations retain all original bytes reversibly, including salt and derived key, under the existing token identity comparator; the comparator and allowlist are unchanged.

The authoring gate protects observable credential ownership, authoritative-session admission, initialized policy/hook ordering and real persistence. Existing public password change/reset tests cannot call this trusted operation or establish physical-versus-virtual authority. No production seam exists solely for tests. Before the feature, the public method was absent: this is capability absence, not an executable regression assertion. An initial provider-only credential selector failed the actual Source owner when a real owned credential row had a foreign account identity (expected two rows, got one); the canonical owner/provider/account predicate repaired that runtime failure. Logs: `/tmp/issue-185-canonical-before.log`, `/tmp/issue-185-authority-proof.log`.

Concurrent null-credential requests both return success, retaining one row. Ordering is controlled through genuine configured hash callback completion: both real hashes finish, the first callback returns, and the second waits until the predecessor's actual SQLite credential write is visible before returning. No fixture supplies results, fabricated receipts or writes, and production is not serialized. The published operation also admits two concurrent missing-account creations; `/tmp/issue-185-source-dual-create.json` retains real Source proof. Native missing-account concurrency requires the separate issue #187 account multiplicity migration and fail-closed global lookup; this PR does not claim it until that prerequisite lands and the owner is rerun. Storage selection among duplicate canonical credentials must retain Source's first scoped physical row. Cross-adapter ordering is unspecified as in the published adapter contract.

Focused Source/native proof: 12 scenarios / 530 assertions before rebase; public API strict all-target Clippy passed after refreshing onto main `941e6917`. Independent coordinator production/authorization review found no ownership defect.

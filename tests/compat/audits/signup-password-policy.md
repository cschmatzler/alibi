# Signup and password policy configuration (issue #182)

This issue follows pinned Better Auth 1.7.6 `api/routes/{sign-up,sign-in,password}.mjs`. Its scope includes signup enablement, auto-sign-in and synthetic duplicate responses, genuine application hash/verifier and existing-user/customization callbacks, initialized length bounds and password reset lifecycle. Arbitrary additional-user-field policies and validateUserInfo remain separate issues #184 and #183; email change/deletion remains #186.

The existing reset owner reproduced three failures on main `e64a2b9cee5a70da97b7ad0c1eb81cd036c0a747`: two generated callback URLs returned 404 and the token-replay owner retained a delivered path mismatch. Native URLs omitted the configured auth base path. The owner-boundary URL repair passes all seven unchanged reset scenarios / 36 assertions. Before/after logs: `/tmp/issue-182-reset-main-e64-before.log`, `/tmp/issue-182-reset-url-after.log`.

The first two configured signup owners pass against the actual Source runtime (two scenarios / 118 assertions). Their complete observations include genuine scrypt callback inputs/results, real account hash bytes, synthetic-versus-physical IDs, SDK/HTTP traces, callback request markers and full physical user/account/session/verification state, including a foreign principal. The baseline native owners fail for the intended reasons: disabled signup removes its route instead of returning the Source coded 400, and autoSignIn false rejects an existing email instead of returning a fresh synthetic user without persistence. Proof: `/tmp/issue-182-configured-source-self-initial.log`, `/tmp/issue-182-configured-signup-before.log`.

The authoring gate protects public configuration, enumeration-safe duplicate behavior, actual callback ordering and persisted credential/session ownership. Existing default signup and email verification owners cannot exercise synthetic customization or observe configured hash/verifier callbacks. All auth behavior remains the published runtime/public native plugins; the private application controls only configure callbacks and inspect or deliberately retire actual stored credentials. No fake crypto, supplied production receipts, comparator/allowlist changes or test-only production interface is used. Implementation and final-head verification are still in progress; this document does not claim full acceptance or canonical completion.

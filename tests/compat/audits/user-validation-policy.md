# User identity validation policy (issue #183)

Reference is actual published Better Auth 1.7.6 `utils/validate-user-info.mjs`, `db/internal-adapter.mjs`, `oauth2/link-account.mjs`, the identity routes, and `@better-auth/core` `types/init-options.d.mts`. Native exposes an optional `AuthConfig.user_validation` implementing the asynchronous `UserInfoValidator` trait. The callback receives a mutable typed `CreateUser` candidate, trusted method/action/provider provenance, and the actual `RequestHookContext`.

Creation through `internalAdapter.createUser` inserts createdAt/updatedAt into the candidate and lowercases its email, then validates with action `create-user` before database hooks. Actual callsites provide methods email-password, anonymous, magic-link, email-otp, phone-number, siwe and admin. OAuth uses the same creation gate with provider metadata. These are actual invocation sites, not inferred callbacks. Returning non-provider sign-ins intentionally do not revalidate the stored identity. New signup may bypass the gate through the already measured enumeration-safe duplicate/synthetic branch rather than creating a user.

OAuth's shared completion validates returning sign-in and implicit linking against fresh mapped provider identity with the existing local user ID and normalized provider email. Metadata contains the raw unmapped provider profile. The implicit-link admission guards run before validation; the explicit-link gate runs before trust/email-match guards. One Tap uses method oauth, providerId google and the actual verified ID-token claims; it has no separate validation method. Existing provider account token/profile writes and session issuance follow the gate. Source's low-level createOAuthUser bypasses this particular creation gate; no native invocation will be invented for that unused helper.

A returned `{error,errorDescription}` rejects with 403 and uses errorDescription when truthy, otherwise the code as its message. Any thrown callback error, including an explicit APIError, becomes 403 validation_failed / User validation failed. Missing method/provider metadata and missing endpoint context have their own closed rejections. Browser route owners can turn a resulting policy APIError into their existing redirect contract. Source signup's enumeration-safe create-user 403 catch can return synthetic success, so policy rejection must be measured in both ordinary and nonautomatic/verification-required signup configuration.

The actual callback can mutate its creation candidate. Trusted changes to name/email/emailVerified/image/createdAt flow unchanged to the database hook and row: even a changed uppercase email is not normalized a second time. Provider sign-in/link validations use fresh copies; mutations to those copies do not replace the identity later persisted by account-linking/profile-update logic. Real SDK owners measure both relationships.

Native's finalized store wrapper owns creation admission, including transactions, before registered creation transforms and database hooks. The opaque `PreparedUserCreation` can only be constructed internally after admission; bundled adapters consume it without a second email normalization. Custom adapters must implement prepared creation, otherwise this trusted mutation contract fails explicitly. Ordinary raw adapter creation still normalizes input. Parsed-input schema defaults precede validation; plugin role transformation follows it; remaining model defaults follow database before hooks. This preserves absent candidate fields on direct creation methods without omitting physical row defaults. Admin creation reads the initialized password maximum/hasher, hashes after admitted user creation, and returns the configured user schema.

The actual original request body and concrete request path remain available. The trusted `ResolvedEndpoint` extension supplies the logical route pattern (`/callback/:id`) separately from concrete `/callback/gitlab`; the native application fixture reads this existing production context for policy and database-hook receipts. It reads typed parsed/transformed body extensions when present, otherwise decodes actual original JSON bytes. This is evidence for the measured built-in bodies, not a claim of universal custom schema body transformation.

Bounds: this typed interface covers the measured built-in candidate fields. Optional string/boolean fields represent an absent or null mapped value as Rust None; raw provider records preserve their original null/presence independently. Arbitrary JavaScript property-presence policies are not claimed equivalent. Source can remove/null candidate timestamps, whereas native explicitly rejects removing required creation dates rather than substituting an invented fallback.
